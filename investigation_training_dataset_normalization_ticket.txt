Title: Investigation: Determine the appropriate spectrogram normalization strategy for EfficientNet

Type: Investigation

Summary
-------
Investigate how TorchSIG spectrogram inputs should be normalized for EfficientNet
training and inference. Per-sample normalization is now optional and disabled by
default because it removes differences in absolute power, noise-floor level, and
SNR between examples. EfficientNet still benefits from a stable and consistent
input distribution, so training-dataset normalization may be a better default.

This ticket is an investigation. It should produce an evidence-based
recommendation and implementation plan; it does not assume that dataset-level
normalization is necessarily superior for every TorchSIG task.

Questions to answer
-------------------
1. What spectrogram representation reaches the model: magnitude, power,
   log-power, or decibels?
2. Should a fixed log or dB transform and clipping range be applied before
   statistical normalization?
3. Should normalization statistics be scalar, per channel, per frequency bin,
   or calculated another way?
4. How should statistics be accumulated without loading the complete training
   dataset into memory?
5. How sensitive are the statistics to dataset configuration, impairment level,
   SNR range, and signal-class distribution?
6. Does dataset-level normalization improve accuracy, calibration, convergence,
   and robustness compared with no normalization and per-sample normalization?
7. How should normalization metadata be stored and validated so validation,
   test, and inference always use the training statistics?
8. How should older checkpoints that used per-sample normalization be handled?

Strategies to compare
---------------------
At minimum, compare:

* No statistical normalization.
* Current per-sample, per-channel mean/std normalization.
* A fixed spectrogram transform followed by global training-set mean/std.
* Per-channel training-set mean/std if multi-channel inputs are supported.

If practical, also evaluate robust scaling or per-frequency-bin statistics.
ImageNet normalization should not be assumed to apply: the current model uses
TorchSIG spectrograms and does not currently load ImageNet-pretrained weights.

Proposed investigation
----------------------
1. Document the exact numerical range and semantics of the current Spectrogram
   transform output.
2. Implement an offline or streaming statistics prototype that reads only the
   training split and uses a numerically stable accumulation method.
3. Record the resulting mean/std and any clipping parameters for a representative
   TorchSIG training configuration.
4. Train comparable EfficientNet runs using identical seeds and hyperparameters
   for each normalization strategy.
5. Evaluate validation and held-out test accuracy, F1, calibration, convergence
   speed, and behavior across SNR ranges.
6. Test inference with shifted gain and noise-floor distributions to measure
   whether gain invariance is helpful or whether absolute-power information is
   important.
7. Estimate the storage, startup-time, and API impact of persisting normalization
   metadata with training artifacts or checkpoints.
8. Recommend a default strategy and a compatibility policy for existing models.

Expected deliverables
---------------------
* A short report describing the input representation and experimental setup.
* Reproducible comparison results for the evaluated strategies.
* Recommended normalization semantics and default behavior.
* A proposed configuration schema, including how statistics are serialized.
* A training/inference consistency plan.
* A checkpoint compatibility and migration recommendation.
* Follow-on implementation tickets if code changes are recommended.

Acceptance criteria
-------------------
* Statistics are derived exclusively from the training split; validation and
  test data do not influence them.
* Every evaluated strategy is applied identically during validation and
  inference.
* The comparison includes no normalization, per-sample normalization, and
  training-dataset normalization.
* Results include overall metrics and performance across relevant SNR ranges.
* The recommendation addresses arbitrary receive gain as well as preservation
  of meaningful power and SNR information.
* The report explains how normalization parameters would be stored with, or
  referenced by, a trained checkpoint.
* No production default is changed as part of this investigation ticket.
